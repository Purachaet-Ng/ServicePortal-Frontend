Raising a ticket — who does what, in what order

Why step 04 is the whole point. There is no form per request type. The chosen type's formSchema array is turned into inputs by src/components/ticket/DynamicForm.jsx and into a matching zod schema at runtime by zodFromFormSchema() in src/lib/formSchema.js. Add a request type in admin, and this page grows a new form with no code change — that is the demo (PLAN.md §5, WORKFLOW.md §A3).

Step 05 never sends department_id. The body is { request_type_id, title, description, priority, custom_fields }. The backend derives the department from the request type, which is what makes "HR department, IT request type" structurally impossible (PLAN.md §5).

⚠ Step 03 is not at the path the spec promises. GET /api/departments/:deptId/request-types is not mounted. What exists is GET /api/request_type — singular, snake_case — and it returns every request type in the organisation with its department nested, so the second dropdown has to be filled by grouping client-side. GET /api/departments and POST /api/tickets both work. Keep the call in src/api/requestTypes.api.js, because the path is expected to change.

The 422 bounce is required, not optional. On 422 VALIDATION_FAILED the response carries details: [{ field, message }], and each one must be mapped onto its input with setError(detail.field, …) — the field names arrive already prefixed, e.g. custom_fields.openings. The pattern to copy is in src/pages/RegisterPage.jsx:71-89.
